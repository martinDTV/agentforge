# 0010. GitHub App dedicada y espejos Git locales (Fase 7, Paso 2)

- Status: accepted (implementado y validado localmente con una API de GitHub simulada; **ninguna App creada ni repositorio real conectado** hasta ejecutar `docs/runbooks/github-app.md`)
- Date: 2026-10-26
- Deciders: martin, Claude (Fase 7)

## Context

El Paso 1 (ADR 0009) dejó el flujo gobernado sobre repositorios locales `sandbox-*`: alcance propuesto por el Scoper, aprobación humana por digest, escritura efímera dentro del worktree, sin remotos. El Paso 2 incorpora el acceso de **solo lectura** a repositorios reales alojados en GitHub mediante una GitHub App dedicada y espejos Git locales, de modo que el Paso 3 pueda publicar ramas y abrir Pull Requests sin cambiar el modelo de seguridad. Decisiones ya tomadas por el usuario: repositorio de prueba privado y desechable `agentforge-sandbox-demo` (distinto de AgentForge y Clivana), GitHub App dedicada con instalación restringida, publicación solo `manual`, `repos:write` solo para humanos, agentes sin credenciales ni acceso a la API de GitHub.

Condiciones añadidas al aprobar este diseño: identidad estable del repositorio por su **id numérico de GitHub** además de `owner/name`, con rechazo de transferencias, sustituciones y cambios de remoto; tokens solo en la plataforma, cortos y con `contents:read` + `metadata:read`, ausentes de argv, URLs, logs, auditoría, checkpoints, archivos y entornos de agentes; revisión del diseño de `GIT_ASKPASS`; agentes y sandbox sin GitHub ni red; espejos con validación de repositorio, remoto, rama base y `base_sha`, bloqueos e idempotencia; contenido remoto como dato no confiable; pruebas con una API simulada; nada real hasta validar en local.

Lo que ya existe y se reutiliza: `RepositoryRegistry` con raíz única y rutas validadas; `LocalGitAdapter` sin shell, entorno saneado (`GIT_ASKPASS=false`, `GIT_SSH_COMMAND=false`, `GIT_TERMINAL_PROMPT=0`, sin `SSH_AUTH_SOCK`, hooks desactivados); worktrees por ejecución; política por repositorio (`app/projects/`); Scoper de solo lectura y aprobación por digest; auditoría por paso; PyJWT con criptografía y `httpx` ya como dependencias.

## Decision

### 1. GitHub App dedicada, instalación restringida, permisos mínimos

- Una App propia de AgentForge, instalada **solo en los repositorios seleccionados** (nunca "todos los repositorios"), empezando por `agentforge-sandbox-demo`. Procedimiento operativo en `docs/runbooks/github-app.md`.
- Permisos del Paso 2: `metadata: read`, `contents: read`. En el Paso 3 se elevará a `contents: write` y `pull_requests: write` únicamente en esa instalación. **Nunca** `workflows`, `administration`, `secrets`, `actions`, `members` ni permisos de organización: sin `workflows`, GitHub rechaza cualquier cambio bajo `.github/workflows` aunque todo lo demás fallara.
- Sin webhooks entrantes en esta fase (sin URL pública ni secreto de webhook): AgentForge solo consulta.
- Settings del **host de la API**: `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY_FILE`, `GITHUB_API_URL` (por defecto `https://api.github.com`; se exige `https://`), `GITHUB_TIMEOUT_SECONDS`, `MIRROR_FETCH_TIMEOUT_SECONDS`. Los dos primeros van juntos o no van; la ruta de la clave debe ser absoluta, no vivir bajo `GIT_REPOSITORIES_ROOT` ni `WORKTREES_ROOT`, y requiere `GIT_REPOSITORIES_FILE`. Al cargar la clave, `GitHubAppCredentials.from_settings` rechaza cualquier archivo que no sea regular, con modo distinto de `0600` o de otro usuario. El `installation_id` y el `github_repository_id` van en la política de cada repositorio (`app/projects/`), nunca en la petición ni en el modelo.

### 2. Identidad estable del repositorio (`app/git/remote.py`, `app/infrastructure/github/identity.py`)

- `RemoteSpec` en la política: `provider=github`, `owner`, `name`, `github_repository_id`, `installation_id`, `default_branch` (debe coincidir con `publish.base_branch`), `fetch_depth` opcional. `owner` y `name` siguen patrones estrictos; la URL **se deriva** (`https://github.com/<owner>/<name>.git`) y no es configurable (`extra="forbid"`).
- Antes de cada `create`/`refresh`/`check` con GitHub configurado, la plataforma consulta `GET /repos/{owner}/{name}` y `GET /installation/repositories` con el token de instalación y aplica `verify_identity`: id distinto bajo el mismo nombre → `repository_substituted`; mismo id bajo otro nombre → `repository_transferred`; ambos distintos → `repository_identity_mismatch`; rama por defecto distinta → `default_branch_changed`; repositorio archivado → `repository_archived`; id fuera de la instalación → `repository_not_in_installation`. Cualquiera de ellos detiene la operación **antes de ningún `fetch`** y, en una ejecución, la termina en `failed` con ese código sin crear worktree.
- El marcador del espejo (`<name>.mirror.json`, `0600`, junto al espejo y fuera de todo checkout) fija `repository_id`, `project_id`, proveedor, `owner`, `name`, `github_repository_id`, `installation_id`, `default_branch`, `remote_url`, `base_sha` y fechas. Si la política deja de coincidir con el marcador (`mirror_identity_mismatch`), o `git remote get-url origin` deja de coincidir con la URL derivada (`mirror_remote_mismatch`), nada se sincroniza: el operador recrea el espejo a propósito. `create` sobre un espejo idéntico equivale a `refresh`; sobre un directorio sin marcador rechaza (`mirror_exists`), nunca adopta.

### 3. Credenciales de corta duración solo en la plataforma (`app/infrastructure/github/`)

- `GitHubAppCredentials` firma el JWT de la App (RS256, `iat` = ahora − 60 s, `exp` = ahora + 9 min) y `GitHubClient` lo canjea en `POST /app/installations/{id}/access_tokens` pidiendo `repositories: [name]` y `permissions: {contents: read, metadata: read}`; si GitHub devolviera más permisos de los pedidos, el token se descarta (`permission_not_allowed`). `InstallationTokenProvider` solo admite los permisos de una lista cerrada (`READ_ONLY_PERMISSIONS`); pedir `contents:write` o `pull_requests` falla en local sin llegar a la red.
- Los tokens viven **solo en memoria** del proceso (`InstallationToken`, cuyo valor solo sale por `reveal()`; `repr`/`str` no lo muestran), con su caducidad (una hora como máximo), renovados al 80 % o si quedan menos de dos minutos, invalidados cuando GitHub los rechaza (`token_invalid` → un canje nuevo y un reintento). Logs y auditoría registran `installation_id`, repositorio y caducidad; jamás el token. `httpx` se crea con `trust_env=False` (sin proxies ni `.netrc`) y los errores llevan código por estado HTTP y ningún cuerpo de respuesta. 5xx y errores de transporte se reintentan una vez.
- `tests/unit/test_github_boundaries.py` recorre `app/` y confirma que solo `app/settings.py`, `app/infrastructure/github/credentials.py` y `app/main.py` nombran `GITHUB_APP_ID`/`GITHUB_APP_PRIVATE_KEY_FILE`; que `app/agents`, `app/tools`, `app/sandbox`, `app/security`, `app/git`, `app/workspaces`, `app/contracts`, `app/projects` y `app/api` no importan `app.infrastructure.github`; que ningún tool expone GitHub, espejos ni `fetch`; que las concesiones de los agentes siguen en `read`; y que el ayudante `GIT_ASKPASS` solo lo cablea el `fetch` del espejo.
- `GitHubClient` expone, además del canje, `installation` (como App: `repository_selection`, permisos, suspensión) y `branch_head` (commit de la rama por defecto), usados solo por el preflight del operador para confirmar que la instalación está restringida y de dónde parte el espejo.
- Los agentes no tienen vía posible: el `LocalGitAdapter` que usan conserva `GIT_ASKPASS=false`; el gateway no registra herramienta alguna de GitHub; el `SandboxRequest` sigue rechazando variables `GITHUB_*` y `GIT_*`; el Runner no tiene red ni cambios en este paso. Los únicos consumidores del token son `MirrorService` (este paso) y el `Publisher` (Paso 3), componentes de plataforma invocados por el orquestador o por el operador.

### 4. Entrega de la credencial a un solo proceso Git (`app/infrastructure/git/askpass.py`)

Revisión del diseño original: en lugar de un único archivo temporal, `askpass_credential(token)` crea un directorio privado `mkdtemp` (`0700`) con dos archivos abiertos con `O_EXCL`: un ayudante ejecutable (`0700`) cuyo shebang es el intérprete actual, y el secreto (`0600`). El ayudante solo responde a prompts de Git que empiecen por `Username` (`x-access-token`) o `Password` (el secreto); abre el archivo con `O_NOFOLLOW`, y rechaza si no es regular, no pertenece al mismo UID o su modo no es exactamente `0600`. La ruta del secreto viaja en `AGENTFORGE_ASKPASS_FILE`; `GIT_ASKPASS` apunta al ayudante; ambas se añaden **solo** al entorno de ese `git fetch` (`env_extra`), que además lleva `GIT_TERMINAL_PROMPT=0`, `credential.helper=` vacío y `protocol.allow=never` salvo `https` (y `file` únicamente en pruebas). El token no aparece en `argv` ni en la URL. En `finally` se sobrescribe el secreto y se elimina el directorio, también si Git falla o se interrumpe. Tokens con saltos de línea o nulos se rechazan antes de tocar el disco.

### 5. Espejos locales (`app/git/mirrors.py`, `app/infrastructure/git/mirror.py`)

- Ruta: `GIT_REPOSITORIES_ROOT/<project_id>/<name>.git` (bare), creado por el operador con `scripts/mirror_repository.py --create` o refrescado por la plataforma, nunca por un agente ni por una petición de la API. Si el espejo está en el registro de repositorios, su ruta y rama por defecto deben coincidir (`mirror_path_mismatch`).
- `refresh`: comprobación de marcador y remoto → verificación de identidad en GitHub → `git fetch --prune --no-tags origin +refs/heads/*:refs/heads/*` (solo ramas; sin etiquetas ni `refs/pull/*`; `--depth` si la política lo fija) → el `HEAD` de `default_branch` pasa a ser el nuevo `base_sha` del marcador (`mirror_base_missing` si la rama no existe). `check` valida marcador, remoto y que la rama local del espejo siga en el `base_sha` registrado (`mirror_base_mismatch`), más la identidad en GitHub si está configurado; sin GitHub, `check` funciona en local y `create`/`refresh` rechazan (`mirror_unconfigured`).
- Concurrencia: un `flock` exclusivo y no bloqueante por repositorio (`<name>.mirror.lock`) serializa `create`/`refresh`/`check` entre procesos del mismo host; el segundo recibe `mirror_locked` en vez de esperar. No se añadió el cerrojo consultivo de PostgreSQL previsto en el borrador: el espejo es un recurso del sistema de archivos del host de la API y un cerrojo en la base de datos no protegería ese recurso frente a otro host; si en el futuro varios hosts compartieran espejos, se revisará aquí.
- Idempotencia: `refresh` sin cambios devuelve `changed=false` con el mismo `base_sha`; `create` repetido es un `refresh`; un `fetch` interrumpido deja el marcador anterior intacto y libera el cerrojo; un `create` fallido elimina el directorio a medias. Un fallo de `git fetch` invalida el token y reintenta una sola vez con uno nuevo; un segundo fallo es `mirror_sync_failed`.
- Integración con la ejecución: `DevelopmentRuntime.refresh_mirror` se ejecuta en el nodo `scoper` **antes** de `WorktreeManager.ensure`, de modo que el worktree `run/<run_id>` parte exactamente del `base_sha` registrado. La propuesta de alcance lleva `base` (`repository`, `github_repository_id`, `branch`, `sha`, `changed`, `synced_at`); `approved_scope.base_sha` se conserva para el Paso 3. Si la política no tiene `remote`, nada de esto ocurre (repositorios `sandbox-*` locales); si lo tiene y la App no está configurada, la ejecución falla con `mirror_unconfigured`. `push` sigue deshabilitado.

### 6. Contenido remoto como dato no confiable (`app/projects/untrusted.py`)

El contenido del repositorio (código, README, docstrings, comentarios, pruebas, salidas de programas) y, más adelante, títulos y cuerpos de issues son **datos no confiables**. Barreras, de dentro hacia fuera:

1. **El modelo no elige acciones.** Ninguna salida del modelo se interpreta como comando, ruta libre o permiso: solo JSON validado contra esquemas cerrados (`ScopeProposal`, `DeveloperChanges`, `QAReview`) y filtrado por la política.
2. **El alcance lo aprueba un humano** por digest; una propuesta "ampliada" por un texto malicioso queda recortada por los globs y visible como rechazo antes de aprobar.
3. **Autoridad efímera y acotada**: aunque el Developer fuese manipulado, solo puede escribir los archivos aprobados, el sandbox no tiene red y el Runner no tiene credenciales.
4. **Archivos de instrucciones para agentes excluidos por defecto** (`DEFAULT_EXCLUDED_CONTEXT_GLOBS`: `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `GEMINI.md`, `.claude/**`, `.cursor/**`, `.cursorrules`, `.windsurfrules`, `.clinerules`, `.aider*`, `.github/copilot-instructions.md`, `.github/instructions/**`, `.agentforge/**`, `agentforge.json`) más los `excluded_context_globs` de cada política: no entran en el listado ni en los archivos clave que ve el Scoper, no se leen para Developer/QA y se rechazan como alcance con motivo `excluded_context`, aunque `writable_globs` los cubriera. La propuesta muestra `hidden_paths`.
5. **Delimitación**: el prompt del Scoper lleva `data_boundary` (texto fijo que declara `paths` y `key_files` como datos) y el sistema del prompt repite que el contenido del repositorio es dato no confiable; los archivos clave van acotados en bytes. No se usan etiquetas `<<repository-content>>` porque el prompt es JSON estructurado.
6. **Detección informativa**: `injection_signals` busca en los archivos mostrados patrones de inyección (ignorar instrucciones en inglés y español, cambio de rol, "system prompt", AgentForge junto a aprobar/escribir/token, exfiltración de secretos, comentarios HTML con instrucciones) y los lista en la propuesta (`signals`, con ruta, patrón y línea) y en el evento `scope_proposed`. No bloquea por sí sola: el bloqueo estructural ya existe.
7. **Issues y PRs ajenos no entran al prompt** en el Paso 2; la salida hacia humanos (cuerpo del PR) se definirá en el Paso 3 desde plantilla y con el texto del modelo escapado.

### 7. Auditoría e idempotencia

- Tabla `mirror_syncs` (migración **0007**, aditiva; el downgrade solo la elimina): una fila por `create`/`refresh`/`check`, con resultado, código, `base_sha`, `previous_sha`, `changed`, identidades, caducidad del token (nunca el token), tiempos y `actor_subject = agentforge:platform`. La escribe `audited()` tanto en éxito como en fallo; `scripts/mirror_repository.py` y el nodo `scoper` pasan por ella.
- Eventos de ejecución: `mirror_refreshed` (repositorio, rama, `base_sha`, `changed`, `executed_by: agentforge:platform`, `actor_subject` nulo) y `scope_proposed` con `base_sha`, `hidden_paths` y número de `signals`. Un fallo del espejo termina la ejecución con `run_failed` cuyo `code` es el de la causa (`repository_substituted`, `mirror_remote_mismatch`, `app_auth_failed`, ...). No se añadió el evento `token_minted` del borrador: el canje se registra en el log de la plataforma y su caducidad en `mirror_syncs`.
- El canje del token está serializado por un cerrojo en memoria del proveedor; dos operaciones concurrentes comparten el mismo token mientras sea válido.

### 8. Prueba inicial con el repositorio privado desechable

1. El usuario crea `agentforge-sandbox-demo` (privado) y la App, la instala solo en ese repositorio con `contents: read` y `metadata: read`, y coloca la clave privada en la ruta configurada (`0600`). Pasos exactos en `docs/runbooks/github-app.md`. AgentForge no crea ni la App ni el repositorio.
2. `scripts/github_preflight.py` (solo lectura) confirma clave `0600`, App, instalación restringida a repositorios seleccionados con permisos exactamente `contents:read` + `metadata:read`, identidad del repositorio por id, commit actual de la rama por defecto, estado del espejo y ausencia de tokens en disco y, con `--scan-db`, en eventos, auditoría y checkpoints. Después, `scripts/mirror_repository.py --create` crea el espejo, verifica la identidad y el remoto derivado, hace el primer `fetch` e imprime `base_sha`; `--check` repite la verificación sin cambios. Las manipulaciones de la tabla del runbook deben fallar con sus códigos.
3. Una ejecución `development` por la API sobre ese repositorio propone el alcance con `base`, el humano lo aprueba, Developer y QA trabajan sobre el worktree local; **nada vuelve a GitHub** en este paso. Criterios de aceptación y evidencia local en `docs/validation/fase7-paso2-criterios.md`.

## Fuera de alcance del Paso 2

`push`, Publisher, creación de PR, comentarios en PR, webhooks, GitLab u otros proveedores, lectura de issues en prompts, repositorios reales distintos del desechable, cerrojos compartidos entre varios hosts.

## Riesgos

- Clave privada de la App en el host de la API: mitigación por permisos de archivo verificados al cargar, Settings estrictas, tokens de instalación de una hora con permisos reducidos por canje, rotación documentada en el runbook.
- Dependencia de la disponibilidad de GitHub: una ejecución sobre un repositorio remoto falla cerrada (`github_unreachable`) en lugar de usar una base sin verificar; el operador puede seguir con repositorios locales.
- Repositorios grandes: `fetch` inicial costoso; mitigación con `fetch_depth` por política y `MIRROR_FETCH_TIMEOUT_SECONDS`.
- Falsa sensación de seguridad con la detección de inyección: por eso es solo informativa y las barreras reales son estructurales.
- Lo validado aquí usa una API simulada y un remoto Git local sobre `file://`: la primera integración real puede revelar diferencias de GitHub (formatos, límites de tasa, 422 en canjes) que se corregirán antes de ampliar a otros repositorios.
